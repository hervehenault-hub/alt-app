# Plan d’implémentation — App d’alternatives écologiques (MVP)

Version du 17 novembre 2026. Source : document « Plan d’implémentation » sur claude.ai.

Ce plan découpe le PRD en 12 lots et environ 120 tâches, chacune réalisable en une session d’agent (1 à 4 h) et vérifiable par une commande ou un test. Il couvre le Must et le Should ; les badges et l’interface commerçants dédiée (Could) en sont exclus.

## Suivi et mode d’emploi économe

**Fait :** vague 1 (T0.1–T0.8, T0.10, T6.1, T6.2, T10.1, T10.4, T11.4), vague 2 (T1.1–T1.10, T2.1–T2.12, T2.15 ; session C : T2.13 conversion pure, T6.4, T7.1, T9.3) et lot 3 (T3.1–T3.8, code prêt ; Apple et Google attendent vos identifiants). **Reste de la vague 2 :** T0.9 (compte Expo à créer). **Lot 4 :** T4.1–T4.9 faits (carte native à valider sur build de développement), T4.10 écrit (Maestro, à lancer sur émulateur). **Démo web :** `pnpm demo:build` (voir `docs/DEMO.md`). **Suite :** T2.14, T2.16, T6.3, T5.8 puis vague 4.

**Pour lancer une tâche avec un minimum de consommation :** une seule session à la fois, nouvelle conversation à chaque lot, consigne courte :

> Lis `CLAUDE.md`, puis réalise les tâches T3.1 à T3.8 décrites dans `docs/PLAN.md` (lis seulement la section du lot concerné). Une PR à la fin, avec un résumé en français simple.

**Modèle conseillé :** Sonnet par défaut ; Opus seulement pour les lots 2, 4 (T4.1), 5 (T5.1, T5.6) et 8 (RLS de la messagerie), où la base de données et la sécurité sont délicates.

## Décisions retenues

| Sujet               | Choix                                                                                                                   | Pourquoi                                                      |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Application mobile  | Expo (React Native) + TypeScript strict, Expo Router, builds EAS                                                        | iOS et Android depuis un seul code, équipe de 1 à 3 personnes |
| Backend             | Supabase en région UE : Postgres + PostGIS, Auth, Storage, Edge Functions, pg\_cron                                     | Offre gratuite, RGPD, requêtes géographiques natives          |
| Carte               | MapLibre React Native + tuiles OpenFreeMap (données OpenStreetMap)                                                      | Pas de clé payante ; impose un development build, pas Expo Go |
| Géocodage           | API Adresse (BAN, data.gouv.fr)                                                                                         | Gratuite, sans clé, précise en France                         |
| Back-office         | Petite app web Vite + React dans le même dépôt                                                                          | Modération sans coût ; hébergement statique gratuit           |
| Tests               | Jest + React Native Testing Library, pgTAP pour la base et les règles d’accès, Maestro pour les parcours bout en bout   | Chaque tâche a un critère vérifiable par l’agent              |
| Compte              | Carte et fiches consultables sans compte ; compte requis pour contribuer, signaler, l’entraide, le parcours et le suivi | Sert l’objectif « première fiche en moins de 30 s »           |
| Mesure              | Table d’événements interne pseudonymisée + vues SQL                                                                     | Pas d’outil tiers payant, données restées en UE               |
| Suivi des plantages | Sentry, offre gratuite, région UE                                                                                       | Indispensable en bêta                                         |

**Hypothèses de travail (modifiables) :** ville pilote Bordeaux (commune de Bordeaux, extensible à la métropole), application nommée « Alt. », trois sessions d’agent en parallèle, langue française uniquement, pas de mode sombre au MVP, couleur secondaire provisoire « bleu ciel pâle » en attendant l’arbitrage, et l’ancien positionnement « Scannez, comparez » reformulé autour de « Trouvez ».

## Conventions

Chaque tâche se lance seule, avec une consigne du type : « Réalise T4.3 du plan ». Elle tient dans une branche et une pull request.

**Lecture des tableaux.** ID = identifiant à citer à l’agent. Livrable = ce qui est produit. Terminé quand = le contrôle que l’agent exécute lui-même avant de rendre la main. Dépend de = tâches à fusionner avant. Une tâche marquée « vous » demande une action ou une validation de votre part.

**Définition de terminé, valable pour toutes les tâches :**

1. `pnpm lint`, `pnpm typecheck` et `pnpm test` passent ; `pnpm test:db` aussi si la base est touchée.
2. Les nouvelles règles métier ont des tests unitaires ; toute nouvelle table a des tests de règles d’accès (RLS).
3. Les écrans ont des libellés d’accessibilité, des cibles tactiles d’au moins 44 points et aucun texte en dur hors du fichier de chaînes `fr.ts`.
4. Aucun secret dans le code ; les variables nouvelles sont ajoutées à `.env.example`.
5. `docs/` est mis à jour si une convention ou une commande change.
6. Une branche `feat/<ID>-<sujet>`, un commit lisible, une pull request qui cite l’ID.

**Ordre.** Les lots s’enchaînent comme sur le schéma ci-dessous ; à l’intérieur d’un lot, suivre l’ordre des ID sauf mention contraire. Avec trois sessions, suivre plutôt les vagues de la section « Répartition sur 3 sessions ».

Ordre : Lot 0 → Lots 1 et 2 → Lots 3, 4, 5 → Lots 6, 7, 8 (+ 9, repoussable) → Lot 10 → Lot 11.

Le lot 0 précède les lots 1 et 2 ; le lot 3 a besoin des profils du lot 2, le lot 4 de la connexion anonyme du lot 3. Le lot 9 peut glisser après la bêta sans bloquer le lancement.

## Répartition sur 3 sessions

Les trois sessions A, B et C avancent par vagues : chacune prend sa colonne, et la vague suivante ne commence qu’une fois toutes les pull requests de la vague fusionnées, CI verte. La session A porte le chemin critique (socle, base, recherche).

| Vague               | Session A                       | Session B                                       | Session C                                                         | Point de synchronisation                                    |
| ------------------- | ------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| V1 · semaine 1      | T0.1 à T0.8, T0.10              | T6.1, T6.2 (contenu JSON, après fusion de T0.1) | T10.1, T10.4, T11.4 (brouillons, après fusion de T0.1)            | socle fusionné, CI verte                                    |
| V2 · semaine 2      | T2.1 à T2.12, T2.15             | T1.1 à T1.10                                    | T0.9, T2.13 (correspondance testée sur fixture), T6.4, T7.1, T9.3 | schéma fusionné, types régénérés                            |
| V3 · semaines 3-4   | T4.1 à T4.10 (T4.3 attend T3.1) | T3.1 en premier, puis T3.2 à T3.8               | T2.14, T2.16 (Bordeaux), T6.3, T5.8                               | parcours Maestro T4.10 vert sur les données de Bordeaux     |
| V4 · semaines 5-6   | T5.1 à T5.7, T5.13              | T6.5 à T6.8, T7.2 à T7.5                        | T5.9 à T5.12, T5.14, T7.6, T11.1                                  | contribution et modération de bout en bout en préproduction |

| V6 · semaines 10-12 | T11.2, T11.3, T11.7, T11.8      | T11.5, T11.6 (tickets répartis)                 | T11.6 (tickets répartis)                                          | lancement à Bordeaux                                        |

**Règles pour éviter les conflits entre sessions**

1. Une session = une branche par tâche ; deux sessions ne touchent jamais le même dossier de fonctionnalité dans une vague.
2. Migrations créées avec `supabase migration new` (nom horodaté) ; avant chaque pull request : rebase sur `main`, `db reset`, `pnpm test:db`.
3. Fichiers partagés découpés par fonctionnalité : chaînes dans `i18n/fr/<fonctionnalité>.ts`, routes dans leur propre dossier ; on ajoute, on ne réécrit pas.
4. Ordre de fusion dans une vague : A, puis B, puis C ; chaque session rebase sur ce qui vient d’être fusionné.
5. Une tâche bloquée par une autre session s’arrête et le signale dans sa pull request plutôt que de recoder la dépendance.
